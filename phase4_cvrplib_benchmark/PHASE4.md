## Experiment B — solution_limit เท่าไหร่ถึงพอ (ตอบคำถามที่เลื่อนมา 3 เฟส)

### วิธีทดลอง

เลือก 3 instance คนละขนาด (small/medium/large) จาก CVRPLIB จริง แล้วลอง `solution_limit` ที่ 200, 500, 1000, 2000 ทุกตัว ภายใต้เพดานเวลาเดียวกัน (90 วินาที) เพื่อดูว่า:
1. Gap ดีขึ้นแค่ไหนเมื่อ limit สูงขึ้น (diminishing returns)
2. ที่ limit=2000 (ค่า freeze ปัจจุบัน) รันจริงถึงเป้าหรือโดนเวลาตัดก่อน

### พบ 3 พฤติกรรมที่ต่างกันโดยสิ้นเชิงตามขนาดโจทย์

**1. E-n51-k5 (50 จุด) — behavior เดียวกับ Phase 1–3:** ถึง solution_limit ทุกค่าจริง Gap ลดลงต่อเนื่อง (10.37% → 3.84%) แต่**ยังไม่ถึง 0%** แม้ที่ limit=2000 — ต่างจาก 4 instance เล็กมากใน Phase 1-3 ที่ได้ 0.00% เป๊ะ นี่คือสัญญาณแรกว่าขนาด 50 จุดเริ่มยากเกินกว่าที่ solution_limit=2000 จะไล่ทันแล้ว

**2. X-n162-k11 (161 จุด) — จุดเปลี่ยน:** ที่ limit=1000 ยังถึงเป้าจริง (44.6s) แต่ที่ **limit=2000 โดนเพดานเวลา 90 วินาทีตัดก่อนถึงเป้า** (`reached_limit=False`) นี่แปลว่า **ค่า config ปัจจุบันของ freeze (2000) ใช้ไม่ได้จริงกับโจทย์ขนาดนี้** — ผลที่ได้ (Gap 3.05%) ไม่ใช่ผลจาก "solver คิดจนสุดทาง 2000 solution" แต่เป็นผลจาก "เวลาหมดพอดี" ซึ่งเป็นพฤติกรรมแบบเดียวกับปัญหา time-limit ที่ Phase 1 พิสูจน์ว่าไม่ deterministic ข้ามเครื่อง — เครื่องช้ากว่านี้จะได้ Gap แย่กว่านี้แน่นอน

**3. X-n459-k26 (458 จุด) — พฤติกรรมที่ 3 ที่ไม่เคยเห็นมาก่อน:** ที่ limit=200 ระบบหยุดเองใน 2.5 วินาที ด้วย `stop_reason=search_exhausted` — คือ **ค้นหมดพื้นที่ค้นหาของตัวเองก่อนจะเจอ solution ที่ดีขึ้นครบ 200 ครั้งด้วยซ้ำ** ไม่เกี่ยวกับเวลาหรือ limit เลย ที่ limit สูงกว่า (500/1000/2000) ล้วนโดนเพดานเวลา 90 วินาทีตัดที่ **ค่าเดียวกันเป๊ะ** (13.44% ทุกตัว, เวลา 90.08s ทุกตัว) เพราะการค้นหาเป็น deterministic เส้นทางเดียวกันเป๊ะ แค่ตัดที่จุดเวลาเดียวกันไม่ว่าจะประกาศเป้าไว้เท่าไหร่

**ข้อสรุปเชิงเทคนิคที่สำคัญที่สุดของ Phase 4:** parameter `solution_limit` ตัวเดียวใช้ไม่ได้กับทุกขนาดโจทย์ ต้อง**ผูกกับขนาดโจทย์** (หรือเปลี่ยนแนวทางเป็นอื่น) ไม่ใช่ค่าคงที่ตัวเดียวแบบที่ freeze ไว้ตั้งแต่ Phase 1 — นี่ไม่ใช่ข้อผิดพลาดของ Phase 1 (ตอนนั้นมีแค่ 4 instance เล็ก ค่า 2000 ใช้ได้จริงกับทุกตัว) แต่เป็นข้อจำกัดที่เพิ่งเห็นได้ตอนขยายขนาดโจทย์ใน Phase 4 นี้เอง

## Experiment A — Gap และ Runtime เทียบกับขนาดโจทย์ (24 instance จริงจาก CVRPLIB)

### ที่มาของข้อมูล

ดาวน์โหลดจาก [VROOM-Project/vroom-scripts](https://github.com/VROOM-Project/vroom-scripts) ซึ่งรวบรวมโจทย์คลาสสิกทั้ง E (Christofides & Eilon) และ X (Uchoa, Pecin, Pessoa, Poggi, Subramanian & Vidal 2014) พร้อมไฟล์ `BKS.json` ที่มี best-known cost + **จำนวนรถจากแหล่งข้อมูลภายนอก** (ไม่ใช่จากชื่อไฟล์หรือ COMMENT ของเรา) — ดู [build_bks_manifest.py](build_bks_manifest.py) และ [bks_manifest.json](bks_manifest.json)

**หลักฐานที่พิสูจน์กฎ "ห้ามเดาจำนวนรถจากชื่อไฟล์" ที่เราถือมาตั้งแต่ Phase 1 อีกครั้ง:** `X-n599-k92` ต้องใช้รถจริง **93 คัน** ไม่ใช่ 92 ตามชื่อไฟล์ และ `X-n936-k151` ต้องใช้ **157 คัน** ไม่ใช่ 151 — ถ้า pipeline เดาจำนวนรถจากชื่อไฟล์เมื่อไหร่ จะพังทันทีกับโจทย์จริงพวกนี้

### ข้อค้นพบที่ 2: เจอ non-determinism จริงจากการรันปกติ 2 ครั้ง ไม่ใช่แค่ทดลองจำลอง (สำคัญมาก)

ระหว่างพัฒนา สคริปต์นี้รันไปครั้งแรกแล้ว crash เพราะบั๊กเล็กๆ ใน print statement (แก้แล้ว) พอรันซ้ำรอบสองด้วย**โค้ดหลังแก้บั๊ก บนเครื่องเดียวกัน ห่างกันไม่กี่นาที** พบว่า 2 instance ได้ผลไม่ตรงกับรอบแรกทั้งที่ config เดิมทุกตัวอักษร:

| Instance | รอบแรก (ก่อนแก้บั๊ก print) | รอบสอง (หลังแก้บั๊ก) |
|---|---:|---:|
| X-n120-k6 | cost=13795 (gap 3.47%) | cost=13679 (gap 2.60%) |
| X-n143-k7 | cost=16465 (gap 4.87%) | cost=16265 (gap 3.60%) |

**ทั้งสองไฟล์นี้หยุดด้วย `stop_reason=time_cap` ทั้งคู่** ส่วนไฟล์อื่นที่หยุดด้วย `time_cap` เหมือนกัน (เช่น X-n106-k14, X-n261-k13) กลับได้ค่าตรงกันเป๊ะทั้ง 2 รอบ

นี่คือ**หลักฐานจากการใช้งานจริง ไม่ใช่การจำลองด้วย CPU โหลดหนักแบบ Phase 1** ที่ยืนยันสิ่งเดียวกัน: **การหยุดด้วยเวลาไม่ deterministic เสมอไป แม้บนเครื่องเดียวกัน** — ผลต่างกันเกิดขึ้นเฉพาะกับ instance ที่การค้นหาไปถึงจุดค้นเจอ solution ใหม่ "พอดีเฉียด" เส้นตาย 30 วินาที (ถ้าเจอก่อนตัดเสี้ยววินาที จะนับ, ถ้าหลังตัดเสี้ยววินาที จะไม่นับ) — ส่วน instance ที่หยุดด้วย `solution_limit` (ไม่ใช่เวลา) ยังคง deterministic 100% เหมือนที่ Phase 1-3 พิสูจน์ไว้ทุกครั้ง

**สรุปให้ชัด:** กฎ "อย่าเชื่อผลลัพธ์ที่หยุดด้วย `time_cap`" ที่ Phase 1/2 เขียนไว้ในโค้ด (`notes` field เตือนไว้อยู่แล้ว) ไม่ใช่แค่การป้องกันไว้ก่อนเผื่อกรณีสมมติ — เจอเคสจริงที่พิสูจน์ว่าจำเป็นทันทีในการรันจริงครั้งแรกของ Phase 4 นี้เอง

## เรื่อง "Best/Average/Worst/Std จาก 10+ รอบ" ที่แผนเดิมขอไว้

แผน (PLAN.md Phase 4) สั่งให้รันซ้ำ 10-30 รอบต่อ instance ถ้า algorithm มี randomness — **core ของเราไม่มี randomness เลย** (พิสูจน์แล้วใน Phase 1: รันซ้ำกี่ครั้งก็ได้ชุดเส้นทางเดิมเป๊ะ ทั้งตอนเครื่องว่างและตอนโหลดหนัก) ดังนั้น "Best/Avg/Worst/Std จาก 10 รอบ" จะเป็น**ค่าเดียวกันทั้ง 10 ค่า, Std = 0** เสมอ — การรันซ้ำ 10 รอบจึงไม่ให้ข้อมูลใหม่กับ core ตัวนี้

นี่เป็นข้อดีจริง (ไม่ต้องเสียเวลารันซ้ำเพื่อหาค่าเฉลี่ยแบบ GA/SA) แต่ก็หมายความว่า **"ความไม่แน่นอน" ของผลลัพธ์ทั้งหมดที่เจอใน Phase 4 นี้มาจากอย่างเดียวคือ `stop_reason` ไม่ใช่ randomness** — เมื่อหยุดด้วย `solution_limit` จะได้ผลเดิมเป๊ะทุกครั้งไม่ว่าเครื่องไหน (พิสูจน์แล้วใน Phase 1-3) แต่เมื่อหยุดด้วย `time_cap` **ผลอาจต่างกันได้แม้รันบนเครื่องเดิมเวลาต่างกันไม่กี่นาที** ("ข้อค้นพบที่ 2" ด้านบน ไม่ใช่แค่ทฤษฎี — เจอจริงระหว่างพัฒนา Phase 4 นี้เอง)
